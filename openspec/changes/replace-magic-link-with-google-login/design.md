# Design

## Context

現在の `signIn` は、Supabase接続モードでは `signInWithOtp` でリンクを送り、ローカルプレビューではそのままログインさせる。戻り先は `location.state.from` で受け取り、`emailRedirectTo` に渡している。

検証で次のことが分かっている。

- `localhost:5173` からのリンクは、Redirect URLsに登録がなくVercel側に移動した
- `.env.local` のSupabaseプロジェクトは、Vercelのデプロイ先と共有している
- `JoinGroupPage` は `/login?returnTo=...` を作っているが、`LoginPage` はこの値を読んでいない

動機と範囲は `proposal.md` を参照する。

## Goals / Non-Goals

**Goals:**

- Googleから戻った後に、元の画面とエラー表示を確実に扱う
- Redirect URLsの登録を少なくする
- 設定とデプロイの順序を間違えても、既存の利用者が締め出されにくくする

**Non-Goals:**

- 認証フローのPKCEへの変更
- メールの確認なしに別のアカウントを統合する機能
- LINEなどのアプリ内ブラウザ向けの機能追加（確認の結果は下記のリスクで扱う）

## Decisions

### 1. Googleからの戻り先を `/login` に統一する

`redirectTo` は `${origin}/login?returnTo=<戻り先>` とする。`LoginPage` がセッション確立後に戻り先へ移動し、失敗時はURLのエラーを表示する。

- **理由:** 保護された画面に直接戻すと、エラー付きで戻った場合に `AuthGuard` がクエリやハッシュを失う。戻り先を `/login` にすれば、エラー表示の場所が1つになる。`JoinGroupPage` が作っている `returnTo` も活かせる
- **代替案:** 元の画面へ直接戻す案は今の方式に近いが、エラー処理が各画面に分散するため採用しない

### 2. 戻り先はアプリ内のパスに限定する

`returnTo` は `/` で始まり、`//` と `/\` で始まらない値だけを受け付け、それ以外は無視する。

- **理由:** `returnTo` はURLから変更できるので、外部サイトへ誘導するオープンリダイレクトを防ぐ
- 優先順は `location.state.from`、`returnTo`、初期画面の順とする

### 3. ログイン処理をモードごとの関数に分ける

`signIn` と `AuthResult` を次の2つに置き換える。

- `signInWithGoogle(redirectPath)`: Supabase接続モード用。デモセッションを終了し、`signInWithOAuth` を呼ぶ。Supabase未設定なら例外とする
- `signInLocal(email)`: ローカルプレビュー用。今の処理を維持する

- **理由:** 戻り値の `magicLinkSent` が不要になる。モードごとに引数が異なるので、関数を分けたほうが誤用しにくい
- 表示の切り替えには既存の `isSupabaseConfigured` と同じ意味の値を使う。`isDemoMode` の命名は対象外なので変更しない

### 4. ログイン画面の表示

スマートフォンを基準に、カード内を次の構成にする。PCでも同じ幅のカードで表示する。

```
Supabase接続:  見出し / 説明 / エラー / [Googleでログイン] / デモの案内
ローカル:      見出し / 説明 / メール入力 / エラー / [ログイン] / デモの案内
```

- Googleのロゴはインラインのsvgで描画し、依存関係を増やさない
- ボタンは指で押しやすい高さとし、横幅いっぱいに表示する
- `authReady` になるまではローダーを表示し、戻ってきた直後にログインフォームが一瞬見えるのを防ぐ
- 不要になる `.magic-link-success` のスタイルを削除する

### 5. ログイン済みの場合の移動

ログイン済みでログイン画面を開いた場合は、戻り先または `/` に移動する。デモ利用者は対象外とする。

- **理由:** Googleから戻る場所が `/login` になるため、この移動が必須になる
- **デモを除く理由:** デモの設定画面にはログイン画面へのリンクがあり、自動で移動するとログイン画面に到達できなくなる

### 6. 既存の利用者の引き継ぎはSupabaseの自動連携に任せる

確認済みの同じメールアドレスは、Supabaseの自動連携で同じユーザーIDになる想定である。アプリに移行のコードは追加しない。

- **理由:** ユーザーIDが変わらなければ、`group_members` とRLSはそのまま機能する。別のアドレスの人は招待リンクで参加し直せるので、利用者の規模に対して移行機能は過剰である
- 実環境で既存アカウントを使って確認する。確認できるまでメールプロバイダーは無効にしない

### 7. スキーマとローカルのデータ

- **スキーマとRLS:** 変更しない。`handle_new_user` トリガーはGoogleのユーザーでも動く。表示名はメールアドレスの `@` より前になる
- **localStorage:** データ形式を変更しない。`STORAGE_KEY` と保存内容はそのまま使う

### 8. ホームページ、プライバシーポリシー、利用規約をアプリ内に置く

Google Cloudの同意画面を本番公開するために必要なページを、アプリのルートとして用意する。

- ホームページは `/login` とする。ログイン画面からプライバシーポリシー（`/privacy`）と利用規約（`/terms`）へリンクする
- `/privacy` と `/terms` は `AuthGuard` の外に置き、すべての動作モードで未ログインでも開けるようにする。静的な表示のみで、データの読み込みは行わない
- 本文は家族・友人向けの小規模なアプリとして簡潔に書く。プライバシーポリシーには、Googleから受け取る情報（メールアドレス、Googleアカウントの識別子）、利用目的（ログインと表示名）、保存先（Supabase）、第三者に提供しないこと、削除の依頼方法を書く。運営者の連絡先は利用者が決める

- **理由:** 同じドメインなので、Google Cloudの承認済みドメインの登録が1つで済み、外部サービスも増えない
- **代替案:** GitHub Pagesなどアプリ外に置く案は、ドメインの登録と管理が増えるため採用しない

## Risks / Trade-offs

- **[LINEなどのアプリ内ブラウザではGoogleログインが拒否される可能性がある]** → 招待リンクはLINEで共有されることが多いと想定されるので、実機で確認する。拒否された場合は、外部ブラウザでの案内を別のchangeとして追加するか、この変更のリリース前に判断する
- **[Googleアカウントのない人がログインできなくなる]** → 利用者の合意のうえで廃止する。リリース前に、アカウントの有無を利用者に確認する
- **[別のアドレスでログインすると、グループやレシピが見えなくなる]** → 利用者に同じアドレスを使うよう案内する。参加し直せばグループのレシピは見えるが、登録者の情報は変わらない
- **[Google Cloudの同意画面が「テスト」状態だと、テストユーザーに登録した人しかログインできない]** → 確認の間は「テスト」のままにし、確認に使うアカウントをテストユーザーに登録する。基本的なスコープのみとし、デプロイ後すぐにホームページ、プライバシーポリシー、利用規約のURLを設定して本番公開に切り替える。デプロイから本番公開までの短い間は、テストユーザー以外はログインできない
- **[設定の順序を誤ると、ログインできない期間が生じる]** → 下記の移行計画の順序で進める

## Migration Plan

1. Google CloudでOAuthクライアントを作成し、リダイレクトURIに `https://<プロジェクトID>.supabase.co/auth/v1/callback` を登録する。同意画面は「テスト」とし、確認に使うアカウントをテストユーザーに登録する
2. SupabaseでGoogleプロバイダーを有効にする。この時点ではメールプロバイダーも有効のままにする
3. SupabaseのRedirect URLsに、本番と開発の `/login` を登録する
4. アプリをデプロイする（プライバシーポリシーと利用規約のページを含む）
5. デプロイ後すぐに、同意画面にホームページ、プライバシーポリシー、利用規約のURLと承認済みドメインを設定し、本番公開に切り替える
6. 既存アカウントで引き継ぎを確認する
7. 確認後にメールプロバイダーを無効にする

**ロールバック:** Vercelで前のデプロイに戻す。手順7より前ならメールプロバイダーは有効のままなので、すぐに元のログイン方法に戻せる。無効にした後は再度有効にする。データの変更はないので、データの巻き戻しは不要である。
