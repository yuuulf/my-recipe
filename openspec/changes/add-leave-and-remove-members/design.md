# Design

## Context

なぜ入れるかは proposal.md、求める動作は `specs/recipe-note-management/spec.md` を参照。いまのコードとデータベース:

- `group_members` には delete のポリシーがなく、利用者はメンバーの行を直接消せない。`groups` も delete・update のポリシーがない
- `recipes` と `group_members` は `groups` に `on delete cascade` でつながっている。レシピの `created_by` は `auth.users` を指すので、メンバーが抜けてもレシピは消えない
- `is_group_member`、`is_group_owner`（security definer）がある。名前の変更は `rename_group`（security definer、`auth.uid()` とオーナーを確かめる）で行っている
- `AppContext` の `loadGroup(user, preferredGroupId?)` は所属するレシピノートを読み直し、覚えているレシピノートがなければ所属がいちばん古いものを開く。どこにも所属していなければ `group` が `null` になり、`GroupGuard` がセットアップ画面に移す
- 設定画面（`SettingsPage.tsx`）は、レシピノートの名前、オーナーとメンバー数、メンバーの一覧、招待リンク、アカウント（ログアウト）を表示する
- 確認の画面は、レシピの詳細画面の削除のものだけで、`RecipeDetailPage.tsx` の中に直接書かれている
- 自動テストは Vitest（部品）と pgTAP（RLS・RPC）がある

## Goals / Non-Goals

**Goals:**

- 退出とメンバーの削除を、サーバー側で権限を確かめる RPC だけで行う
- 退出の後に開くレシピノートを、いまの「覚えている → いちばん古い → セットアップ画面」の流れで決める
- 確認の画面を共通の部品にし、退出・削除・レシピの削除で同じ見た目と操作にする

**Non-Goals:**

- オーナーの譲渡、招待リンクの作り直し、ほかにメンバーがいるレシピノートの削除（proposal の対象外）
- 外された人の画面への即時の反映（Realtime などは使わない）
- メンバー一覧以外の画面（ヘッダーの切り替えなど）からの退出

## Decisions

### 1. RPC を2つ追加する（マイグレーション）

`supabase/migrations/20261115000000_add_leave_and_remove_member.sql` を追加する。どちらも `security definer`、`set search_path = public` で、`rename_group` と同じ書き方にする。`public` と `anon` から実行の権限を外し、`authenticated` にだけ与える。

**`leave_group(p_group_id uuid) returns text`**

1. `auth.uid()` がなければ「ログインが必要です。」（`28000`）
2. `select ... from groups where id = p_group_id for update` でレシピノートの行をロックする。同時に誰かが参加しても、退出の判定と食い違わないようにするため（参加の `group_members` への追加は、外部キーの確認で同じ行を共有ロックするので、ここで待つ）
3. 自分がメンバーでなければ「このレシピノートのメンバーではありません。」（`42501`）
4. 自分がオーナーのとき
   - ほかにメンバーがいれば「ほかのメンバーがいる間、オーナーは退出できません。」（`55000`）
   - 自分だけなら `groups` の行を削除する。メンバーとレシピは `on delete cascade` で消える。`'deleted'` を返す
5. オーナーでなければ、自分の `group_members` の行を削除し、`'left'` を返す

**`remove_group_member(p_group_id uuid, p_user_id uuid) returns void`**

1. `auth.uid()` がなければ `28000`
2. 自分がそのレシピノートのオーナーでなければ「レシピノートのオーナーだけがメンバーを外せます。」（`42501`）。存在しないレシピノートも、ここで拒否される
3. 外す相手が自分なら「オーナー自身は外せません。」（`22023`）
4. 相手がメンバーでなければ「このメンバーはレシピノートにいません。」（`22023`）
5. 相手の `group_members` の行を削除する

- RLS のポリシーは追加しない。直接の削除は、いまどおり拒否される
- テーブルの形は変わらないので、`seed.sql` には影響がない。`npm run db:reset` で当たることを確かめる
- 外された人のプロフィールは、レシピノートを共有しなくなるので、残ったメンバーから見えなくなる（`profiles_select` のポリシーのとおり）。レシピの登録者は「メンバー」と表示される

戻り値で `'left'` と `'deleted'` を分けるのは、テストで動きを確かめやすくするため。画面はどちらの場合も読み直すだけなので、戻り値では分岐しない。

### 2. AppContext に退出と削除の関数を足す

`AppContextValue` に次を足す。どちらもデモモードではエラーを投げる（画面には操作を出さないが、念のため）。

- `leaveGroup(groupId: string): Promise<'switched' | 'signed_out'>`: `leave_group` を呼んだ後、所属するレシピノートを取り直す。残っていれば `loadGroup(user)` で読み直して `'switched'` を返す。覚えているレシピノートは抜けたものなので見つからず、所属がいちばん古いものが開く。1つも残っていなければ `signOut` でログアウトして `'signed_out'` を返す（利用者の判断で追加。セットアップ画面に置き去りにしないため）
- `removeMember(groupId: string, userId: string): Promise<void>`: `remove_group_member` を呼んだ後、開いているレシピノートのメンバーを読み直す（`membersLoading` の流れを使う）

設定画面は、退出の後に、`'switched'` なら `/recipes`、`'signed_out'` なら `/login` に移る。

### 3. 共通の確認の画面

`src/components/ConfirmDialog.tsx` を作る。いまのレシピの削除の確認と同じ見た目（中央のカード、危険の色のアイコン、キャンセルと実行のボタン、背景を押すと閉じる）。

- props: `title`、`description`、`confirmLabel`、`icon`、`loading`、`error`（失敗の文言）、`onConfirm`、`onCancel`
- `role="dialog"`、`aria-modal="true"`、`aria-labelledby` を付ける。実行中は背景やキャンセルで閉じない
- `RecipeDetailPage.tsx` の削除の確認も、この部品に置き換える（見た目と動きは変えない）
- クラスはいまの詳細画面のものをそのまま移す。新しい色やトークンは足さない

### 4. 設定画面の操作

スマホ幅を基準にする。PC でも同じ配置で、カードの並びだけがいまどおり2列になる。

**メンバーを外す**

- オーナーで、デモモードでないときだけ、メンバーの一覧の自分以外の行の右端に、外すボタン（`UserMinus` のアイコン、`aria-label`「〇〇を外す」）を出す。いまの役割の表示（オーナー・メンバー）の右に置く
- 確認: 見出し「〇〇さんを外しますか？」、本文「このレシピノートのレシピを見られなくなります。登録したレシピは残ります。」、ボタン「外す」
- 失敗したときは、確認の画面の中にエラーを出す

**退出**

- 招待リンクのカードの下に、「レシピノートから退出」のカードを1枚足す（`col-span-full`）。デモモードでは出さない
- メンバーを読み込んでいる間は、退出のボタンを無効にする（オーナーがほかのメンバーといるかを判定できないため）
- オーナーでないメンバー: 説明「退出すると、このレシピノートのレシピを見られなくなります。」、ボタン「退出する」
- ほかにメンバーがいるオーナー: ボタンを無効にし、「ほかのメンバーがいる間は、オーナーは退出できません。メンバーを外すと退出できます。」を出す
- 1人だけのオーナー: 説明「退出すると、このレシピノートとレシピはすべて削除されます。」、ボタン「削除して退出する」
- 確認: メンバーは見出し「「レシピノート名」から退出しますか？」、本文「登録したレシピは残ります。もう一度参加するには招待リンクが必要です。」、ボタン「退出する」。1人だけのオーナーは見出し「「レシピノート名」を削除しますか？」、本文「レシピノートとレシピはすべて削除され、元に戻せません。」、ボタン「削除して退出する」
- ボタンは、いまの `Button` の `danger` と `ghost` を使う

### 5. セットアップ画面のログアウト

どのレシピノートにも所属していないと、いまはセットアップ画面からほかの画面に行けず、ログアウトもできない（初めてログインした利用者も同じ）。セットアップ画面のカードの下の「〇〇 で作成します」の行の右端に、同じ大きさ（12px、16px のアイコン）の文字のボタン「ログアウト」を置き、`signOut` の後に `/login` に移る。どのアカウントで使っているかの隣にあるので、別のアカウントで入り直したいときに見つけやすい。作成のボタンより目立たせないため、ボタンの形にはしない。メールアドレスが長いときは、アドレスと「で作成します」の間で先に折り返し、とても長いアドレスだけがアドレスの途中で折り返す（利用者と相談して決定。カードの下の大きな枠なしボタン、カードの右上、アイコンの行の順に試した）。

退出で所属が0になったときは自動でログアウトする（決定2）。ほかの理由（外された、など）で所属が0になってセットアップ画面に来た利用者は、このログアウトを使う。

### 6. テスト

- **pgTAP**（`supabase/tests/leave_and_remove.test.sql`）
  - メンバーの退出と、退出後にそのレシピノートが見えないこと
  - ほかにメンバーがいるオーナーの退出の拒否
  - 1人だけのオーナーの退出で、レシピノートとレシピが消えること
  - 所属していないレシピノートからの退出の拒否
  - オーナーによる削除と、外された人のレシピが残ること
  - オーナーでない人による削除の拒否、オーナー自身の削除の拒否、メンバーでない相手の拒否
  - ログインしていない利用者の拒否
  - 直接の削除がいまどおり RLS で拒否されること
- **Vitest**
  - `ConfirmDialog`: キャンセル、背景、実行、実行中は閉じない
  - `SettingsPage`: オーナーにだけ自分以外の外すボタン、メンバーには出ない、デモには退出も外すも出ない、ほかにメンバーがいるオーナーは退出が無効、1人のオーナーは「削除して退出する」、確認の後に `leaveGroup` と `removeMember` が呼ばれる、所属が残れば `/recipes`、残らなければ `/login` に移る
  - `SetupPage`: ログアウトで `signOut` が呼ばれ `/login` に移る

## Risks / Trade-offs

- [Risk] 外された人がその時点で画面を開いていると、次に読み込むまでレシピノートが表示されたままになる → その間にレシピを開いたり保存したりしても、RLS で拒否されるか空になる。次にアプリを開くと、所属していないレシピノートとして扱われる
- [Risk] 外された人が、同じ招待リンクで参加し直せる → proposal の対象外として明記している。必要になったら、招待リンクの作り直しを別の変更で入れる
- [Risk] 1人だけのオーナーが誤って退出すると、レシピが戻らない → 確認の画面で削除されることを見出しとボタンの文言で示す
- [Trade-off] オーナーは、ほかにメンバーがいる間は抜けられない。抜けたいときは、ほかのメンバーを全員外す必要がある → 譲渡は対象外。運用の規模（家族や友人）では困らないと判断した

## Migration Plan

1. 手元で `npm run db:reset` を流し、マイグレーションと `seed.sql` が当たることと、`npm run db:test` が通ることを確かめる
2. マージの前後に、利用者が本番の Supabase にマイグレーションを当てる（`npx supabase db push` か SQL Editor）。関数を足すだけなので、アプリのデプロイとの順番はどちらでもよい。ただし、当てる前にアプリが出ると、退出と削除の操作はエラーになる
3. 戻すときは、2つの関数を `drop function` する。テーブルとデータの形は変わらない
