# Design

## Context

移行の目的は proposal.md の Why を参照。

- `src/main.tsx` が `index.css`（リセットと基本の文字設定）と `App.css`（`:root` の変数と全画面のスタイル）を読み込んでいる。CSS Modules やインラインの `style` は使っていない
- `App.css` のレスポンシブ指定は、ほとんどが `max-width`（1199px / 760px / 640px）で、`min-width: 961px` が1か所ある。つまりPC表示を基準にして、スマートフォン向けに上書きする書き方になっている
- `className` のうち条件で変わるものは7か所ある。`Button` の `button-${variant}`、入力欄の `has-error`、タグの `selected`、役割の `role-pill ${member.role}`、`NavLink` の `active` である
- 疑似要素は6か所ある。ログイン画面の背景の円、区切り線、必須項目の `*`、作り方の手順をつなぐ線である。回転アニメーションは `spin` を0.7秒と0.8秒で使っている
- 見出しや段落の一部は、ブラウザの既定のスタイルに頼っている。たとえば `.page-header p` は余白を指定しておらず、`.empty-state h2` は太さを指定していない
- 文字の太さに 650、750 などの中間値を使っている。Webフォントは読み込んでおらず、実際の表示はOSのフォント（ヒラギノなど）に依存する
- 自動テストはなく、見た目の確認はブラウザで手動で行う
- この変更はlocalStorageのデータ形式とSupabaseのスキーマに関係しない

## Goals / Non-Goals

**Goals:**

- `App.css` をなくし、スタイルを各コンポーネントの `className` で完結させる
- デザインの値（色、角丸、影、文字サイズ、ブレークポイント）を `index.css` のテーマに集め、直書きの値を残さない
- スマートフォン表示を基準にした書き方（モバイルファースト）にそろえる
- 移行前後の見た目の差を、スクリーンショットの比較で確認できるようにする

**Non-Goals:**

- `tailwind.config.js` を使う設定（v3の方式）
- 新しいデザインの値（新色、新しい余白の体系）の導入
- `clsx`、`tailwind-merge` などの補助ライブラリの導入
- クラスの並び順を自動で整える仕組み（Prettierのプラグインなど）。このプロジェクトにはフォーマッターがない

## Decisions

### 1. Tailwind v4のCSSファーストの設定を使う

`tailwindcss` と `@tailwindcss/vite` を入れ、`vite.config.ts` にプラグインを追加する。設定は `src/index.css` の `@import 'tailwindcss'` と `@theme` に書き、JavaScriptの設定ファイルは作らない。

- 代替案: PostCSSのプラグイン。Viteのプラグインのほうが設定が少なく、ビルドも速いため採らない
- 代替案: v3と設定ファイル。新規の導入でv3を選ぶ理由がないため採らない

### 2. `:root` の変数をテーマのトークンに置き換える

`App.css` の変数を、Tailwindの名前空間に合わせたトークンに移す。

```
--primary          -> --color-primary          (bg-primary, text-primary ...)
--primary-hover    -> --color-primary-hover
--primary-soft     -> --color-primary-soft
--background       -> --color-background
--surface          -> --color-surface
--surface-muted    -> --color-surface-muted
--text             -> --color-text
--text-secondary   -> --color-text-secondary
--text-muted       -> --color-text-muted
--border           -> --color-border
--border-strong    -> --color-border-strong
--danger           -> --color-danger
--blue / -soft     -> --color-info / --color-info-soft
--shadow-sm / -md  -> --shadow-sm / --shadow-md   (既定値を上書き)
--radius-sm/md/lg  -> --radius-sm / --radius-md / --radius-lg (6 / 8 / 10px)
```

- 互換用の別名（`--ink`、`--orange`、`--green` など）は移さない。参照箇所は対応するトークンに置き換える
- 既定のカラーパレット（`red-500` など）は `--color-*: initial` で無効にし、テーマにない色を使えないようにする

### 3. 変数を通さない色の扱い

`:root` の外にある直書きの色は、次の順で扱う。

1. 主色の透明度違い（`rgba(52, 120, 89, .1)` など）: `bg-primary/10` のような不透明度の修飾子にする
2. 複数の箇所で使う色（危険操作の背景 `#fff5f2`、その枠線など）: `--color-danger-soft`、`--color-danger-border` のようなトークンを追加する
3. 1か所だけの色で、近いトークンや不透明度の修飾子で見分けがつかないもの: そのトークンに寄せる。見分けがつく場合だけトークンを追加する

移行後の `className` には、`[#...]` のような任意の色の値を書かない。

### 4. ブレークポイントを今のしきい値で定義する

既定のブレークポイントを無効にし、今のしきい値をモバイルファーストの最小幅として定義する。

```
既存 (max-width)              テーマ (min-width)
max-width: 640px  の上書き -> base (〜640px)  /  sm: 641px 以上
max-width: 760px  の上書き -> base (〜760px)  /  md: 761px 以上
min-width: 961px           ->                    lg: 961px 以上
max-width: 1199px の上書き ->                    xl: 1200px 以上
```

スマートフォン向けの値を接頭辞なしで書き、広い画面の値を `md:`、`lg:` などで足す。サイドバーとモバイルの下部ナビゲーションの切り替え（761px）など、今の切り替え位置は変えない。

- 代替案: Tailwindの既定値（640 / 768 / 1024 / 1280px）。切り替え位置が変わると見た目が変わるため採らない
- 代替案: `max-md:` などで今の上書きの書き方を残す。スマートフォンを基準にする方針に合わないため採らない

### 5. 文字サイズ、角丸、太さをそろえる

- 文字サイズ: 既定のスケールを無効にし、実際に使う値でスケールを定義する（11 / 12 / 13 / 14 / 15 / 16 / 18 / 20 / 24 / 26 / 28 / 30px）。それ以外の値は最も近い値に寄せ、差が同じなら大きいほうにする（17→18、19→20、23→24、27→28、29→30）。`clamp()` を使う見出し（ページ見出しとレシピ詳細の料理名）は、任意の値で `clamp()` を残す。38px はこの `clamp()` の上限だが、レシピ詳細の番号（`#XX`）も 38px で、30px に寄せると見た目が大きく変わるため、スケールに追加する（実装中に追加）。寄せたことで改行の位置が変わる箇所（スクリーンショットで確認する）は、レイアウトが変わるため元のサイズを残し、そのサイズをスケールに追加する（実装中に追加: 17px。ログイン画面の説明の見出しが390pxで改行の位置が変わったため）
- 角丸: `7px` は `rounded-md`（8px）、`20px` と `50%` は `rounded-full` にする
- 太さ: 650 は `font-semibold`（600）、750 は `font-bold`（700）、800 は `font-extrabold` にする。対象のフォントで表示が変わる場合は、その箇所だけ任意の値で元の太さを残す
- 字間（`letter-spacing`）と行の高さ: 値の種類が少ないため、使っている値をそのまま任意の値で書く。使う箇所が多い値だけトークンにする

### 6. 繰り返すスタイルはコンポーネントにまとめ、`@apply` は使わない

- `Button` は `variant` ごとのクラスを、コンポーネント内のオブジェクトで持つ
- 入力欄、カード、見出しラベル（eyebrow）など、複数の画面で同じクラスを使う部品は、`src/components/` のコンポーネントにするか、クラス文字列の定数にする
- 条件で変わるクラスは、テンプレートリテラルで組み立てる。`Button` に外から渡す `className` は、幅や余白などの重ならないクラスに限る

- 代替案: `@apply` で今のクラス名を残す。クラスの定義がCSSに残り、移行の目的（クラスの所在を追いやすくすること）に反するため採らない
- 代替案: `clsx` と `tailwind-merge`。条件のあるクラスは7か所だけなので、追加しない

### 7. ベーススタイルとプリフライトの違い

Tailwindのプリフライトは、見出しの大きさと太さ、段落と見出しの余白、リストの記号などをリセットする。今のスタイルはこの一部をブラウザの既定に頼っているため、移行する要素には大きさ、太さ、余白を明示する。`index.css` のリセット（`box-sizing`、フォームの `font: inherit`、`a` の色、選択範囲の色など）は `@layer base` に移す。プリフライトと重なるものは削除する。

### 8. アニメーションと疑似要素

- 回転: 今の速さ（0.7秒と0.8秒）を保つため、`@theme` に `--animate-spin-fast` などを定義する。既定の `animate-spin`（1秒）には寄せない
- 疑似要素: `before:` / `after:` の修飾子で書く。ログイン画面の背景の円のように指定が長いものは、`aria-hidden` の装飾用の要素に置き換えてもよい

### 9. 移行の進め方

既存のCSSは `@layer` の外にあり、Tailwindのユーティリティ（`@layer utilities`）より優先される。そのため、まず Tailwind を導入して `App.css` と併用し、画面ごとに独自クラスをユーティリティに置き換える。置き換えた分のルールは、そのたびに `App.css` から削除する。最後に `App.css` と `main.tsx` の読み込みを削除する。

```
[導入+テーマ] -> [共通部品: Button, AppShell, Loading, LegalPage]
             -> [画面: ログイン, セットアップ, 招待, 一覧, 詳細, 登録/編集, 設定, 規約]
             -> [App.css の削除]
```

共通部品を先に移すのは、複数の画面で使われるためである。

### 10. 見た目の確認方法

移行の前に、ローカルプレビューとデモで各画面のスクリーンショットを撮っておく。幅は 390px、800px、1280px の3つで、761〜960px の間でしか出ない表示も確かめる。移行後に同じ条件で撮り、比較する。エラー表示、空の一覧、確認ダイアログなど、操作しないと出ない表示も対象にする。Supabase接続モードだけの表示（Googleログインのボタンなど）は、Supabase接続で確認する。

## Risks / Trade-offs

- [プリフライトにより、既定のスタイルに頼っていた余白や見出しの大きさが変わる] → 移行する要素ごとに明示し、スクリーンショットで比較する
- [値をそろえたことで1〜2pxずれる] → proposal で許容している範囲。レイアウトの崩れ（折り返し、はみ出し）がないことを各幅で確認する
- [移行途中で `App.css` のルールとユーティリティが競合する] → 置き換えた要素から独自クラスを外し、該当するルールを同時に削除する
- [`Button` に外から渡すクラスが内部のクラスと競合する] → 渡すクラスを幅や余白に限る。競合が必要になった場合は、`variant` か props を追加する
- [`className` が長くなり、JSXが読みにくくなる] → 繰り返す部品はコンポーネントや定数にまとめる（Decision 6）
- [`docs/DESIGN_IMPLEMENTATION_PLAN.md` が実装と食い違う] → 過去の計画として残す。必要なら後で更新する

## Migration Plan

- データとスキーマの移行はない。デプロイはビルド結果の差し替えだけ
- 元に戻す場合は、この変更のコミットをrevertする。依存の追加とCSSの変更だけなので、データには影響しない
